## Product design

### Goals / Non-goals

Goals:
- Give Agent-platform agents (via the MCP Gateway) read access to RunZero's asset inventory and vulnerability-exposure data, and the ability to trigger a network scan on a RunZero site — the three capabilities named in the ticket.
- First version: 5 tools covering sites, assets, vulnerabilities, starting a scan, and listing scans (so a started scan can be polled).

Non-goals (first version):
- No write/delete of inventory data, no asset tagging or custom-field editing.
- No organization/user administration (RunZero's Account API).
- No OAuth2 client-credentials flow — first version accepts only a pre-generated Bearer token via a single Header (matches the "credential only from Header" contract and the `/api/vendor-register` constraint that new vendors must be "normal", fixed-key-Header vendors, not OAuth).
- No CSV export tool — JSON only.
- No software/wireless/certificate inventory tools — not among the ticket's three named capabilities; candidates for a follow-up ticket if requested.

### Acceptance criteria AC1..AC8

- AC1: Given a valid RunZero API Bearer token in the `X-Runzero-Api-Token` Header, When an agent calls the "list assets" tool (optionally with a search filter and/or a site scope), Then it receives a bounded list of RunZero assets (id, names, addresses, OS, risk/vulnerability summary) with a total/has_more indicator, sourced from RunZero's Export API.
- AC2: Given a valid token, When an agent calls the "list sites" tool, Then it receives the list of RunZero sites in the organization (id, name), needed to scope a scan or an asset query.
- AC3: Given a valid token and a site id, When an agent calls the "start scan" tool, Then RunZero starts a scan task for that site and the tool returns the scan id and status; the tool is marked non-read-only/non-idempotent and requires an explicit site id (no "scan everything" default).
- AC4: Given a valid token, When an agent calls the "list scans" tool, Then it receives recent scan tasks with their status (queued/running/complete/failed), so a caller can poll a scan started under AC3.
- AC5: Given a valid token, When an agent calls the "list vulnerabilities" tool (optionally scoped to an asset or site), Then it receives vulnerability-exposure data (finding id, CVE, severity, affected asset) drawn from RunZero's data.
- AC6: Given a request is missing the RunZero credential Header, When any tool is called, Then the service returns the structured 401 contract (not a 500), listing the required Header name in the body.
- AC7: Given an invalid/expired token or a RunZero-side error (429/5xx), When any tool is called, Then the error is mapped to the structured envelope (`unauthorized` / `rate_limited` / `upstream_error`) with `retryable` set correctly — never a raw stack trace or an unhandled exception.
- AC8: Given two different tenants' requests arrive with two different tokens, When their tools execute, Then neither can observe the other's token or data (request-level isolation; no shared/global state).

### Open questions

- [assumed, not blocking] The exact JSON shape and upstream path for vulnerability data (AC5) were not confirmed against the live OpenAPI spec — the SwaggerHub link 404'd during this design pass (see "Current state"). This design assumes vulnerability exposure is obtainable either via a dedicated export-style endpoint or via vulnerability fields embedded in the asset export record. The dev leg must re-resolve the spec (via `help.runzero.com/docs/` → the linked "runZero API HTML (ZIP)"/PDF bundle, or a working SwaggerHub/GitHub mirror) before implementing `runzero_list_vulnerabilities`, and use whichever is accurate. This does not change the tool-level contract in "Data & API contract" (tool name, inputs, output shape stay the same regardless of which upstream endpoint backs it) — only §4's change list and the client code are affected if the real shape differs.
- [assumed, not blocking] This design assumes a single credential Header is sufficient for all 5 tools, i.e. the same token can read exports and start scans. If a tenant's actual RunZero license separates Export Tokens (read-only) from Organization Tokens (read-write), a caller using an Export Token will simply get a 401/403 from RunZero on `start_scan` only — handled by the existing structured-error contract (AC7); no second Header is needed to make this correct.

## Tech design

### Conclusion

New MCP server, Python 3.12 + uv + FastMCP, built in the already-created empty repo `MSPbotsAIFramework/runzero-mcp`. Five tools map closely to RunZero's Export API (assets, sites, scans) and Organization API (start scan); vulnerability exposure is served by a fifth tool backed by whichever RunZero endpoint actually carries vulnerability data (to confirm at build time, see Open questions). Credentials: one Header, `X-Runzero-Api-Token`, carrying the Bearer token created in the RunZero console. No OAuth, no local state, no database — a thin read/trigger proxy in front of RunZero's REST API, the same shape as every other single-token vendor MCP in this org.

### Where the current implementation lives

There is no existing implementation. `MSPbotsAIFramework/runzero-mcp@main` (`d935a8b`) contains only the 2-line placeholder README described in "Current state" — verified via `git log` in the read-only worktree (single "Initial commit" by Cavin Lang). No sibling repo in the org was opened as a structural reference for this design; the canonical shape to follow is the skeleton in `~/.claude/skills/vendor-mcp-development/reference/vendor-mcp-development-sop.md` §9, which every vendor MCP in this org is built from. This is a clean-room build from RunZero's official docs — the open-source `runZeroInc/runzero-api` client is reference-only (vendor-mcp-development rule 3: no fork, no import, no code translation from vendor open source).

### Data & API contract

Credential Header:

| Header | Required | Type | Description |
|---|---|---|---|
| `X-Runzero-Api-Token` | yes | password | RunZero Bearer token (Export, Organization, or Account token) created in RunZero Console → Account → API |

`runzero_list_sites`
- Input: `{}` (no filters in v1 — site counts are small; add `search` later if needed)
- Maps to `GET /export/org/sites.json`
- Output: `{"sites": [{"id": str, "name": str}], "total": int}`

`runzero_list_assets`
- Input: `{"site_id": str | null, "search": str | null, "limit": int = 50 (max 200), "offset": int = 0}`
- Maps to `GET /export/org/assets.json` with RunZero's `search` query parameter; the export endpoint's native pagination support was not confirmed during this design (see Open questions) — if it has none, the service fetches once and slices client-side, still bounded by `limit`/`offset` and the ≤20000-char response cap (SOP §2).
- Output: `{"assets": [{"id": str, "names": [str], "addresses": [str], "os": str | null, "risk": str | null, "vulnerability_count": int | null}], "total": int, "has_more": bool}`

`runzero_list_vulnerabilities`
- Input: `{"asset_id": str | null, "site_id": str | null, "limit": int = 50 (max 200), "offset": int = 0}`
- Maps to whichever RunZero endpoint carries vulnerability data per the OpenAPI spec (Open questions); the output contract below is endpoint-independent.
- Output: `{"vulnerabilities": [{"id": str, "cve": str | null, "severity": str, "asset_id": str, "description": str}], "total": int, "has_more": bool}`

`runzero_start_scan`
- Input: `{"site_id": str}` (required, no "all sites" default — this is a mutating action and must be explicit)
- Maps to `PUT /org/sites/{site_id}/scan`
- Output: `{"scan_id": str, "status": str}`
- Hints: `readOnlyHint=false`, `idempotentHint=false`.

`runzero_list_scans`
- Input: `{"site_id": str | null, "limit": int = 50 (max 200), "offset": int = 0}`
- Maps to `GET /export/org/scans.json`
- Output: `{"scans": [{"id": str, "site_id": str, "status": str, "started_at": str | null, "completed_at": str | null}], "total": int, "has_more": bool}`

Errors: all 5 tools return the structured envelope `{"error": {"code", "message", "retryable"}}` on failure, never raise. `code` is drawn from the fixed vocabulary (`unauthorized`, `not_found`, `invalid_argument`, `rate_limited`, `upstream_error`; `not_configured` is not applicable since the Header is validated at the middleware layer, not per-tool).

Backward compatibility: first version of a new service, no prior contract to break.

### Key flow / sequence

```
Agent -> Gateway: tools/call runzero_list_assets {search: "os:windows"}
Gateway -> runzero-mcp (POST /mcp, Header X-Runzero-Api-Token: <tenant token>)
runzero-mcp: middleware sets ContextVar(token) -> tool handler
runzero-mcp -> RunZero (GET /export/org/assets.json?search=os:windows, Authorization: Bearer <token>)
RunZero -> runzero-mcp: 200 + asset JSON array
runzero-mcp: maps to {"assets": [...], "total", "has_more"}; ContextVar reset in finally
runzero-mcp -> Gateway -> Agent: tool result
```

`runzero_start_scan` follows the same shape with `PUT /org/sites/{id}/scan` and a write-intent response (`scan_id`, `status`).

### Non-functional

- Idempotency/concurrency: all tools except `start_scan` are read-only and naturally idempotent; `start_scan` is explicitly marked non-idempotent (calling it twice starts two scans — RunZero's own semantics, not something to mask). No state is held across calls, so concurrent requests from different tenants never interleave.
- Performance: list outputs capped at `limit<=200` (default 50), total response ≤20000 chars with `has_more`; connect/read timeouts 5s/30s. The asset export endpoint is the main latency risk if RunZero returns an entire org's inventory in one call — see the pagination note in "Data & API contract".
- Security: the token is read only from `X-Runzero-Api-Token`, stored in a per-request `ContextVar`, never logged, never written to disk or environment variables; `/health` does not call RunZero, so it never leaks reachability information about a tenant's RunZero instance.
- Multi-tenant isolation: the container serves many tenants concurrently; isolation is structural (ContextVar set/reset per request, no module-level client holding a token, no cross-request cache keyed by anything other than the current request).
- Observability: structured logs include tool name, RunZero HTTP status, and the mapped `code`/`retryable` on error — never the token value or the raw response body (which may contain tenant inventory data).

### Risks & dependencies

- Risk: the SwaggerHub spec link 404'd during this design (the asset/site/scan endpoints are independently confirmed via `help.runzero.com/docs/leveraging-the-api`, so the other 4 tools are not at risk; only the vulnerability endpoint's exact shape is unconfirmed). Mitigation: the dev leg re-resolves the spec before implementing `runzero_list_vulnerabilities`; the tool contract is endpoint-independent, so no design rework is needed either way.
- Risk: RunZero's daily API rate limit equals the licensed asset count — a chatty agent loop could burn the quota. Mitigation: bounded `limit`/pagination per tool keeps each call cheap; no auto-polling loop is built into the tools beyond the single-call backoff in `runzero_client.py`.
- Dependency: none on other tickets or repos. No gateway change needed — `mcp-service-gateway@main` (read-only reference) already routes a single static per-tenant credential Header, which is exactly this vendor's shape.

### Decisions made by DEV01

- Picked 5 tools (sites, assets, vulnerabilities, scans-list, scan-start) instead of mirroring every RunZero REST endpoint. Alternatives considered: 1:1 endpoint mirroring (Option C, rejected — exceeds tool-count guidance for no ticket-driven need) and a single generic query tool (Option B, rejected — worse agent discoverability and hint granularity).
- Picked a single credential Header (`X-Runzero-Api-Token`) over separate Export/Organization-token Headers. Alternative: two Headers, one for read tools and one for `start_scan`. Chose one Header because the ticket does not call for least-privilege separation, and RunZero itself already rejects a read-only token on the write endpoint (surfaced via the existing structured-error contract, AC7) — a second Header would add complexity with no concrete requirement driving it. Adding a second optional Header later is a non-breaking, additive change if this turns out to matter.
- Picked JSON-only export, no CSV tool. Alternative: mirror RunZero's `.csv` variants. Chose JSON-only because MCP tool outputs must be structured and token-economical (SOP §2); CSV offers no benefit to an agent caller.
- Deferred OAuth2 client-credentials support. Alternative: support both Bearer-token and OAuth2 in v1. Chose Bearer-token-only because `/api/vendor-register` only supports "normal" vendors authenticated via a fixed-key Header, not OAuth, and every other single-token vendor MCP in this org is registered the same way.
- Scoped out RunZero's Account API (org/user administration). Alternative: include org/user admin tools. Excluded because the ticket's three named capabilities (discovery, scanning, vulnerability exposure) do not include administration, and the Account API requires a Platform license tier not confirmed to be available for this integration.

### Deviations from the tech design (implementation detail, user-visible behaviour unchanged)

1. **Flat keyword arguments instead of one Pydantic input model per tool.**
   The design said "each tool takes a single Pydantic input model... so new
   optional filters can be added later without breaking existing callers."
   Tested empirically: registering a tool with a single `BaseModel` parameter
   produces a JSON Schema that nests all fields under a wrapper key (e.g.
   `{"args": {"site_id": ...}}`), which is *not* how an MCP caller naturally
   invokes a tool (flat `{"site_id": ...}`) — worse for agent discoverability
   (SOP §2.4). Using `Annotated[..., Field(...)]` keyword arguments directly
   produces the expected flat schema, keeps full Pydantic validation
   (`ge`/`le`/descriptions), and is equally forward-compatible: a new optional
   keyword argument with a default does not break existing callers either.
2. **`mcp[cli]` resolved to 2.3.0, where `FastMCP` is renamed `MCPServer`.**
   The design and the vendor-mcp-development SOP's Python reference (§7, §9)
   describe the v1 API (`mcp.server.fastmcp.FastMCP`, `Mount()` with the
   lifespan wired to an outer app). `pyproject.toml` pins `mcp[cli]>=1.9.0,<3.0.0`
   per the SOP's "lock a major version" guidance; `uv sync` resolved the
   current 2.x release. `mcp.server.mcpserver.MCPServer.streamable_http_app()`
   in this version returns one complete `Starlette` app with its lifespan
   already wired to the session manager, rather than a sub-app meant to be
   mounted into a second outer app. `/health` is appended as a route on that
   same app object instead of being combined via `Mount()` — there is only
   one app and one lifespan, so the "`Mount()` doesn't run the child's
   lifespan" pitfall (SOP §7) does not apply here. Verified: a stateless
   `tools/list` call (no `initialize`) returns 200, which would be 400 if the
   session manager's lifespan had not actually started.
3. **Added `app/paging.py`** (not itemized in the design's change list) as a
   small shared helper for the limit/offset slicing and 20,000-char response
   cap that `list_assets`, `list_vulnerabilities`, and `list_scans` all need —
   avoids three copies of the same truncation logic (DRY); purely internal,
   no change to any tool's input/output contract.
